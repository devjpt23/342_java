1. Project Overview
You are provided with starter code for a small Java 25 application that retrieves current temperature
information from the Open-Meteo weather service and displays it for several predefined cities. The starter
program works, but it combines several responsibilities in one source file: location configuration, HTTP
communication, response parsing, error handling, application control, and presentation.
Your task is to refactor the prototype into a well-designed, testable, extensible command-line weather
information system. The goal is not simply to add features. Your design should demonstrate the software
design principles discussed in class.

Central Design Question
If the real weather API were replaced with a completely different source of weather data, how much of
your program would you have to rewrite?
A strong design should require changes primarily to the provider implementation—not to the command-line
interface, application logic, or unit tests for that logic.

5. Starter Application
The supplied Main.java defines several locations, creates an HttpClient, builds and sends a request to OpenMeteo, extracts temperature data from the JSON response, and renders a simple text bar.
The starter code should be treated as a prototype to refactor, not as the architecture of your final solution. In
particular, your final design must separate networking, weather-data access, application logic, command
processing, and presentation.
Important: the starter parser returns 72.0 when a temperature cannot be found. Your refactored application
must not silently replace missing or malformed data with a believable fake value. Parsing and provider failures
must be handled explicitly.

6. Weather API and Data Research
The starter code uses the Open-Meteo Forecast API. You are expected to examine the API documentation and
determine which additional weather measurements are useful for your application.
Open-Meteo Forecast API documentation: https://open-meteo.com/en/docs
The API supports current, hourly, and daily weather variables. Examples include relative humidity, apparent
temperature, precipitation, weather codes, pressure, cloud cover, wind speed, wind direction, and wind
gusts. Research the documentation rather than limiting your implementation to the temperature field used in
the starter code.

7. Required Architecture
Your solution must use the package and source organization shown in Section 8. You may add additional
classes when they improve the design, but you may not collapse the required responsibilities into fewer
classes.

Weather Data Provider
Create a WeatherDataProvider interface that represents a source of weather information. Application logic
must request weather information through this abstraction rather than directly through HttpClient.
Create OpenMeteoWeatherProvider as the concrete production implementation. It is responsible for
communicating with Open-Meteo and converting API responses into your application's model objects.

Weather Service
Create WeatherService to contain weather-related application logic. WeatherService must receive a
WeatherDataProvider through its constructor. It must not construct OpenMeteoWeatherProvider internally.

This constructor-based dependency injection must make it possible to supply a mock or test implementation

Weather Data Model
Use records/classes in the model package to represent locations and weather information. Raw JSON strings
must not be passed through the rest of the application.

Command-Line Interface
WeatherCLI is responsible for reading commands, validating input, calling service methods, and displaying
results. It must not directly communicate with the remote API. Service classes should return information
rather than print directly to the console.

Application Startup
Main.java is the composition root: it should create the production provider, construct WeatherService with
that provider, construct the CLI, and start the application.

13. Java 25 Suggestions
Java 25 provides several language features that may make parts of this project clearer or more concise. You
are encouraged to consider these features where they fit naturally, but you are not required to use a specific
number of them.
•
•
•
•
•

Records — useful for immutable model objects such as Location or WeatherData.
Enhanced switch expressions — useful for interpreting CLI commands or mapping values to categories.
Pattern matching — useful when it simplifies type checks or command/result handling.
Text blocks — useful for a multi-line help screen, usage instructions, or formatted output.
var — useful for local variables when the type is obvious and readability is preserved.
Modern collection APIs and streams — useful for filtering locations, finding the warmest/coldest location,
calculating comparisons, or formatting results.
Modern instanceof patterns — useful when type checking is actually needed and avoids unnecessary
casts.

Use modern Java features because they improve the design or readability of your solution, not simply to
demonstrate syntax. Threads and concurrency have not been covered and must not be used in this project.

14. Error Handling
Your application must fail gracefully and provide useful feedback. Consider unknown commands, missing
arguments, unknown locations, network failures, unsuccessful HTTP status codes, malformed/missing API
data, and invalid weather values.
Do not silently substitute fake data when parsing or communication fails. Choose an appropriate errorhandling strategy and make failures visible to the appropriate layer.
